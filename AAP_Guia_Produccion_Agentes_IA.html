1. Introducción y Contexto

AAP V1 Laboratory es una plataforma de runtime para agentes definidos por datos. A diferencia de frameworks tradicionales donde el comportamiento de los agentes vive en código Python, aquí los agentes se definen completamente en JSON Schema — sin cambios de código, sin recompilación, sin despliegue de nuevas versiones de aplicación.

Esta guía te llevará desde cero hasta un agente IA en producción ejecutándose en la nube, con inferencia remota (modelos como GPT-4, Claude, o tu propio modelo local via VRAM alquilada).

Nota Importante: Esta guía asume que tienes acceso a:
  • Docker Desktop o Docker Engine en tu máquina local
  • Créditos/API key de un proveedor de LLM (OpenAI, Anthropic, o VRAM remota)
  • Bash/PowerShell para ejecutar comandos

2. Arquitectura de Producción en la Nube

La arquitectura de AAP V1 se divide en tres capas:

Capa de Datos

3 Bases de Datos SQLite

  • control.db — Definiciones
  • runtime.db — Ejecuciones
  • domain.db — Datos del dominio

Almacenadas en volúmenes Docker persistentes

Capa de Ejecución

Worker Process

  • Polling cada 2s
  • Executor (L0-L3)
  • Policy Engine

Procesa runs asincronamente

Capa de API

FastAPI + UI

  • REST endpoints
  • Dashboard web
  • Nunca bloquea

200 requests/s sin problemas

Proveedores Recomendados para Inferencia Remota

Proveedor Modelos Disponibles Latencia Típica Coste Estimado Mejor Para
OpenAI API GPT-4, GPT-3.5, o1 800ms - 2s $0.03-$0.30/1K tokens Producción, máxima calidad
Anthropic (Claude) Claude 3 Opus, Sonnet, Haiku 1-3s $0.003-$0.048/1K tokens Razonamiento, contexto largo
Together AI Llama 2, Mistral, Zephyr 200-800ms $0.0002-$0.009/1K tokens Bajo coste, privacidad
RunPod/Lambda Labs Tu propio modelo (fine-tuned) 100-500ms $0.14-$1.22/hora GPU Modelos personalizados

Seleccionar Proveedor: Matriz de Decisión

Pregúntate:
  • ¿Necesitas máxima precisión? → OpenAI GPT-4 o Claude Opus
  • ¿Buscas equilibrio coste/calidad? → Claude Haiku o Mistral 7B
  • ¿Tienes datos sensibles? → Self-hosted (RunPod) o Together AI
  • ¿Ejecutas miles de requests/día? → Llama/Mistral local + RunPod
  • ¿Es un POC o MVP? → OpenAI API (fácil de escalar)

Configuración de Credenciales en Producción

# Crear archivo .env.production (NUNCA en Git) export OPENAI_API_KEY="sk-..." export ANTHROPIC_API_KEY="sk-ant-..." export TOGETHER_API_KEY="..." # En docker-compose.yml (NO hardcodes) environment: - OPENAI_API_KEY=${OPENAI_API_KEY} - ANTHROPIC_API_KEY=${ANTHROPIC_API_KEY} - AAP_DATA_DIR=/data
Seguridad Crítica: Nunca commitees API keys en Git. Usa variables de entorno o secret managers (AWS Secrets, HashiCorp Vault, GitLab CI/CD secrets).

4. Docker: Conceptos Esenciales para AAP V1

¿Por Qué Docker es Clave?

Docker empaqueta AAP V1 + dependencias + configuración en un contenedor reproducible. Esto significa que lo que funciona en tu máquina, funciona exactamente igual en producción, en AWS, en tu servidor en la nube, o en cualquier lugar.

Analógía: Si tu aplicación fuera un barco, Docker es el puerto de carga (contenedor) que permite transportarlo idéntico a cualquier destino sin que se dañe.

Componentes de Docker en AAP V1

Componente Función En AAP V1
Dockerfile Receta para construir la imagen Define cómo instalar deps, copiar código, exponer puerto 8080
Imagen Snapshot del código + dependencias aap:local (construida localmente)
Contenedor Instancia ejecutándose de la imagen API container + Worker container (2 procesos)
Volumen Almacenamiento persistente ./data → las 3 BD sobreviven restart
Red Comunicación entre contenedores API ↔ Worker comparten localhost:8080

El Dockerfile de AAP V1 Explicado

FROM python:3.11-slim WORKDIR /app # Instalar dependencias del sistema RUN apt-get update && apt-get install -y --no-install-recommends \ git curl && rm -rf /var/lib/apt/lists/* # Copiar código fuente COPY . . # Instalar dependencias Python RUN pip install -e ".[prod]" # Crear directorio de datos (volumen) RUN mkdir -p /data # Exponer puerto de la API EXPOSE 8080 # Punto de entrada: el comando que ejecuta al iniciar CMD ["uvicorn", "aap.api.main:app", \ "--host", "0.0.0.0", "--port", "8080"]

docker-compose.yml: Orquestación de Servicios

version: '3.9' services: api: image: aap:local ports: - "8080:8080" environment: - AAP_DATA_DIR=/data - OPENAI_API_KEY=${OPENAI_API_KEY} volumes: - aap_data:/data depends_on: - worker networks: - aap_network worker: image: aap:local environment: - AAP_DATA_DIR=/data - OPENAI_API_KEY=${OPENAI_API_KEY} volumes: - aap_data:/data command: python -m aap.worker.main networks: - aap_network volumes: aap_data: driver: local networks: aap_network: driver: bridge

5. Configuración Local/Remota Paso a Paso

5.1 Instalación Local (Desarrollo)

1 Clonar el Repositorio
git clone https://github.com/tu-org/aap-v1.git cd aap-v1
2 Crear Entorno Virtual
python -m venv .venv source .venv/bin/activate # En Windows: .venv\Scripts\activate
3 Instalar Dependencias
pip install -e ".[dev]"
4 Crear Archivo de Configuración
cp .env.example .env # Editar .env con tus API keys export OPENAI_API_KEY="sk-..." export AAP_DATA_DIR="$(pwd)/data"
5 Iniciar API en Local
uvicorn aap.api.main:app --reload --port 8080 # En otra terminal: python -m aap.worker.main
Éxito: Abre http://localhost:8080 y verás el Dashboard. Si ves "Agentes" vacío, ¡estás listo!

5.2 Despliegue en la Nube con Docker

1 Construir la Imagen
docker build -t aap:v1.0 . # Verificar que la imagen se creó docker images | grep aap
2 Crear Archivo de Variables de Entorno
cat > .env.production << 'EOF' OPENAI_API_KEY=sk-your-key-here ANTHROPIC_API_KEY=sk-ant-your-key-here AAP_DATA_DIR=/data EOF # Proteger el archivo chmod 600 .env.production
3 Iniciar Contenedores
docker-compose up -d # Ver logs en tiempo real docker-compose logs -f # Verifica que ambos servicios estén Up docker-compose ps
4 Validar Conectividad
curl http://localhost:8080/health # Respuesta esperada: { "status":"ok", "api":true, "worker":true, "db":true }

5.3 Despliegue en Servidor en la Nube (AWS/GCP/Azure)

Opción A: Usar Managed Containers (Recomendado para producción)

  • AWS ECS Fargate: Configurar task definition con la imagen Docker, montar volumen EFS para datos
  • Google Cloud Run: Soporta contenedores con almacenamiento efímero (BD en Cloud SQL)
  • Azure Container Instances: Despliegue rápido, facturación por segundo

Opción B: Docker Compose en EC2/VM (Más control, más responsabilidad)

# En tu servidor (EC2 Ubuntu, DigitalOcean, Linode, etc.) # 1. Instalar Docker sudo apt-get update sudo apt-get install -y docker.io docker-compose # 2. Clonar repo git clone https://github.com/tu-org/aap-v1.git /opt/aap-v1 cd /opt/aap-v1 # 3. Crear .env con keys de producción sudo nano .env.production # 4. Montar volumen para persistencia (importante) sudo mkdir -p /mnt/aap_data sudo chown -R ubuntu:ubuntu /mnt/aap_data # 5. En docker-compose.yml, apuntar a volumen externo volumes: aap_data: driver: local driver_opts: type: none o: bind device: /mnt/aap_data # 6. Iniciar servicios docker-compose --env-file .env.production up -d # 7. Configurar Reverse Proxy (Nginx/Let's Encrypt para HTTPS)

6. Ciclo de Vida Completo: Fabricación de Agentes

6.1 Ciclo Conceptual

┌──────────────────────────────────────────────────────────────┐ │ VISIÓN DE PRODUCTO │ │ "Queremos un agente que haga X" │ └────────────────────────────┬─────────────────────────────────┘ │ ▼ ┌──────────────────────────────────────────────────────────────┐ │ DEFINICIÓN (JSON Schema) │ │ │ │ ├─ identity: nombre, descripción, tags │ │ ├─ goal: objetivo y criterios de éxito/fallo │ │ ├─ runtime: autonomy_level, iteraciones, presupuesto │ │ ├─ brain: modelo LLM, temperatura, reasoning │ │ ├─ tools: qué herramientas pueden usar │ │ ├─ knowledge: fuentes de información │ │ └─ policies: red, BD, shell, presupuesto │ └────────────────────────────┬─────────────────────────────────┘ │ ▼ ┌──────────────────────────────────────────────────────────────┐ │ CREAR VERSIÓN v1 │ │ │ │ POST /agents (crear identidad) │ │ POST /agents/{id}/versions (crear v1) │ │ │ │ → Guardada en control.db, inmutable │ └────────────────────────────┬─────────────────────────────────┘ │ ▼ ┌──────────────────────────────────────────────────────────────┐ │ PRUEBAS Y AJUSTES │ │ │ │ POST /agents/{id}/runs (ejecutar v1) │ │ GET /runs/{id} (ver resultado) │ │ GET /runs/{id}/events (revisar paso a paso) │ │ │ │ → Si funciona → Promover v1 a ACTIVE │ │ → Si no → Crear v2 con cambios │ └────────────────────────────┬─────────────────────────────────┘ │ ▼ ┌──────────────────────────────────────────────────────────────┐ │ MONITOREO CONTINUO │ │ │ │ GET /agents/{id}/metrics (tasa de éxito, coste) │ │ GET /agents/{id}/compare (v1 vs v2 - cuál mejor?) │ │ │ │ → Si regresión → Revert a versión anterior │ │ → Si mejora → Celebrar, documentar, iterar │ └──────────────────────────────────────────────────────────────┘

6.2 Estructura de una Agent Definition

Toda Agent Definition sigue un schema único (el Pydantic model en aap/core/definition/models.py). Aquí está desglosada cada sección:

{ "schema_version": 1, "id": "my-agent-slug", // Identity: quién es este agente "identity": { "name": "Customer Support Bot", "description": "Atiende consultas de clientes...", "owner": "your-team", "tags": ["support", "customer-facing"] }, // Goal: qué intenta lograr "goal": { "statement": "Resolver consultas de clientes en menos de 2 minutos", "success_criteria": [ { "type": "metric", "expr": "customer_satisfaction >= 4.5" } ], "failure_criteria": [ { "type": "metric", "expr": "response_time > 300" } ] }, // Runtime: cómo se ejecuta "runtime": { "autonomy_level": 2, // L2 = Plan antes de ejecutar "max_iterations": 5, "concurrency": 1, "resumable": true, "fixed_steps": [] // Vacío = flexible, no secuencia fija }, // Brain: qué LLM usar y cómo "brain": { "primary": { "capability": "standard", // GPT-4 o equivalente "temperature": 0.2, // Bajo = más determinista "use_for": ["plan", "react"] }, "reasoning": { "capability": "cheap", // Haiku o equivalente "temperature": 0.2, "use_for": ["evaluation"] }, "response_format": "tool_calling" }, // Tools: qué puede hacer "tools": [ { "id": "search.web", "config": { "max_results": 5 } }, { "id": "db.query.customers", "config": {} }, { "id": "email.send", "config": {} } ], // Policies: qué puede y no puede hacer "policies": { "network": { "mode": "allow", "domains": ["api.example.com", "*.internal.test"] }, "database": { "domain_db": "allow", "tables": ["customers", "orders"] }, "budget": { "max_steps": 20, "max_tool_calls": 10, "max_tokens": 100000, "max_money_usd": 0.50, "max_wallclock_s": 300 } }, // Triggers: cuándo se ejecuta "triggers": [ { "type": "manual" // Manual = desde API/UI } ] }

7. Ejemplos Prácticos Paso a Paso

7.1 Crear Tu Primer Agente: "FAQ Bot"

Un agente que responde preguntas frecuentes usando un documento PDF como fuente.

1 Definir el Agente (JSON)
{ "schema_version": 1, "id": "faq-bot", "identity": { "name": "FAQ Bot", "description": "Responde preguntas comunes" }, "goal": { "statement": "Encontrar la respuesta correcta en el FAQ", "success_criteria": [] }, "runtime": { "autonomy_level": 1, "max_iterations": 1 }, "brain": { "primary": { "capability": "standard", "temperature": 0.1 } }, "tools": [ { "id": "knowledge.search", "config": { "top_k": 3 } } ], "policies": { "budget": { "max_steps": 5, "max_tool_calls": 2, "max_tokens": 10000, "max_money_usd": 0.05 } } }
2 Crear el Agente (CLI o UI)
# Vía CLI: python -m aap.cli.main create-agent faq-bot "FAQ Bot" python -m aap.cli.main create-version faq-bot definition.json # Vía UI: # 1. Abre http://localhost:8080 # 2. Haz clic en "+ Crear agente" # 3. Rellena el formulario # 4. Haz clic en "Guardar"
3 Ejecutar (Trigger)
curl -X POST http://localhost:8080/agents/faq-bot/runs \ -H "Content-Type: application/json" \ -d '{ "input": { "question": "¿Cuál es tu política de devoluciones?" } }' # Respuesta: { "run_id": "abc123def456...", "status": "queued" }
4 Monitorear Ejecución
# Esperar 2-5 segundos (worker pickup) curl http://localhost:8080/runs/abc123def456 # Ver eventos paso a paso: curl http://localhost:8080/runs/abc123def456/events # Ver herramientas ejecutadas: curl http://localhost:8080/runs/abc123def456/tool_calls

7.2 Modificación: FAQ Bot v2 con Redacción

La v1 funcionó, pero queremos que NO muestre información sensible. Creamos v2 con políticas más restrictivas.

# Cambio en policies: "policies": { "network": { "mode": "denied" // No acceso a web }, "budget": { "max_steps": 3, // Menos pasos "max_money_usd": 0.02 // Más barato } } # Crear v2: python -m aap.cli.main create-version faq-bot faq-bot-v2.json # Comparar v1 vs v2: curl http://localhost:8080/agents/faq-bot/compare?a=1\&b=2 # Promover v2 si está bien: curl -X POST http://localhost:8080/agents/faq-bot/versions/2/promote

9. Diagnóstico y Resolución de Problemas

Problema: Worker No Ejecuta Runs

Síntomas:

  • POST /runs retorna 202 ✓
  • Pero GET /runs/{id} sigue en "queued" después de 5 minutos

Diagnóstico:

# 1. ¿Worker está corriendo? docker-compose ps | grep worker # 2. ¿Hay errores en los logs? docker-compose logs worker | tail -50 # 3. ¿Base de datos accesible? docker-compose exec worker python -c \ "from aap.config import runtime_db_path; print(runtime_db_path())"

Solución:

  1. Reiniciar Worker: docker-compose restart worker
  2. Verificar BD: Asegurar que el volumen `aap_data` está montado
  3. Aumentar logging: Añadir `--log-level DEBUG` en comando del worker

Problema: API Lenta / Timeouts

Síntomas:

  • GET /agents tarda > 10 segundos
  • Intermitente (a veces rápido, a veces lento)

Diagnóstico:

# 1. ¿Servidor saturado? docker stats aap_api # 2. ¿Queries lentas en BD? docker-compose exec api python -c \ "from aap.core.definition.repository import list_agents; \ import time; t=time.time(); list_agents(); print(time.time()-t)" # 3. ¿Network issues? docker network inspect arquitecturaalfa1_aap_network

Solución:

  1. Aumentar CPU/RAM: En docker-compose, añadir límites
  2. Indexar BD: Crear índices en tablas frecuentes
  3. Caché: Implementar Redis para agentes frecuentes

Problema: Datos Perdidos Después de Restart

Síntomas:

  • Antes del restart: 100 runs en la BD
  • Después del restart: 0 runs

Diagnóstico:

# 1. ¿Volumen persiste? docker volume ls | grep aap_data # 2. ¿Ruta correcta? docker inspect arquitecturaalfa1-api-1 | grep -A 3 "Mounts" # 3. ¿Permissions? ls -la /var/lib/docker/volumes/aap_data/_data/

Solución:

  1. Verificar volumen: docker volume inspect aap_data
  2. Backup antes de reiniciar: cp -r ./data ./data.backup
  3. Usar volumen externo: Apuntar a /mnt o /var/aap-data en el host
